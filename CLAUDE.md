# Clerk — Project Rules

Read `PRODUCT_SPEC.md` before making architectural decisions. These rules are permanent; the spec has the full detail.

## Remote repository (critical)

The final destination is the existing `Anant-Madhok231/clerk-ai` repo and its Pages site — both frozen until the owner explicitly authorizes migration. Never run `git remote add`, `push`, `push --force`, `gh repo create/delete`, or anything that touches GitHub Pages/Releases settings without that explicit authorization in the current conversation. `git remote -v` should be empty during the rebuild.

## Architecture

- One conceptual Clerk agent. Do not introduce named sub-agents (`EmailAgent`, `SupervisorAgent`, etc.) — separate modules are fine, a multi-agent architecture is not.
- Don't scaffold packages ahead of need. A `packages/*` split is justified only when a second real consumer outside `apps/desktop` needs the same code.
- `AIProvider` has exactly two implementations: `DemoAIProvider`, `OpenAIProvider`. No speculative hosted-provider stub class.

## AI outputs

Every model classification response is validated against a Zod schema before it touches persistence. Never parse free-form model text into application state. Bounded retries on schema-validation failure; never write malformed output to SQLite.

## Credentials

OAuth tokens and API keys go through Electron `safeStorage` only. Do not add `keytar` or another native credential store unless a concrete, reproducible `safeStorage` limitation is hit and documented — not as a precaution. Never log tokens, API keys, or authorization headers. Never place secrets in source, `localStorage`, or committed files.

## Demo Mode

Demo Mode must run fixture `SourceItem`s through the real ingestion → matching → classification → reconciliation → persistence → UI pipeline, with only the AI classification step swapped for deterministic `DemoAIProvider` logic. Never inject prebuilt `Situation` objects directly into the UI.

## Verification discipline

Never report a phase, test, build, or deployment as done without actually having run it and observed the result in this environment. Distinguish clearly between: implemented, mocked, locally verified, built, not yet tested, and requires external credentials or another OS's CI to verify. No fabricated test results, releases, or screenshots.

## Code quality

Domain-named files over generic ones (`utils.ts`, `helpers.ts`). Comments explain *why*, never *what*. No AI-boilerplate comments, no "Generated by Claude" markers in source files. No abstraction layers beyond what current code actually needs.
